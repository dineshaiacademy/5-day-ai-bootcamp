📊 Evaluation & Observability: Proving Your AI App Works, and Watching It in Production

Reading time: about 25 minutes  |  Lab: 3-Evaluating_LLM_Outputs.ipynb  |  Level: Beginner to Intermediate

🎯 Learning objectives

By the end of this section you will be able to:

  1. Explain the difference between evaluation (testing before you release) and observability (watching after you release).
  2. Build an eval dataset and score answers with three methods: reference-based, LLM-as-a-judge and human review.
  3. Evaluate an agent on more than its final answer: task success, correct tool use and number of steps.
  4. Calculate a pass rate and use it to catch a regression.
  5. Describe what to record for every production request (logs, traces, metrics) and what you must never record.

1. Two questions every AI app must answer

🧪 EVALUATION

Question: "Is my app good enough to release?"

When: Before release, and again after every change.

Input: a fixed test set that you write.

Output: a score, such as a pass rate of 90%.

🔭 OBSERVABILITY

Question: "What is my app actually doing for real users right now?"

When: After release, all the time.

Input: real user traffic.

Output: logs, traces, dashboards and alerts.

Real-world analogy: a new car.

Car AI application
Crash tests and a test track run in the factory before the car is sold Evaluation: run a fixed test set before every release
The dashboard warning lights and the trip computer while you drive Observability: metrics and alerts from real traffic
A mechanic reads the car's error log to find out why the engine light came on Tracing: follow one request step by step to find the cause of a problem

⚠ You need both. Evaluation only tests the cases you thought of. Observability shows you the cases you did not think of, and those become new eval cases. Section 10 shows how the two feed each other.

PART A · 🧪 EVALUATION (before release)

2. Why "it looked right when I tried it" is not enough

Most beginners test an AI app by typing a few questions and reading the answers. This is called vibes-based testing. It only tells you about one version of the app on one day.

❌ Vibes-based testing ✅ Systematic evaluation
1. Try question A. Looks good.
2. Try question B. Looks good.
3. Change the system prompt.
4. Release it and hope.
Do A and B still work? Nobody knows. 		1. Write a fixed test set (questions + expected answers).
2. Run every question through the app.
3. Score every answer automatically.
4. Compare the score with the last run.
If anything broke, the score drops and you see it at once.

This is the same idea as unit tests in normal software. The difference is that an AI answer is rarely one exact string of text, so we need smarter ways to decide if an answer is "correct". Sections 4 to 6 cover them.

3. Step 1: build an eval dataset

Definition: An eval dataset (also called a test set or golden set) is a fixed list of prompts, each paired with the expected answer or expected behaviour.

This is the dataset used in the lab notebook:

eval_dataset = [
    {"prompt": "What is the capital of France?",                  "expected": "Paris"},
    {"prompt": "What is 12 multiplied by 8?",                     "expected": "96"},
    {"prompt": "Who wrote the play Romeo and Juliet?",            "expected": "William Shakespeare"},
    {"prompt": "What is the boiling point of water in Celsius, at sea level?",
                                                                  "expected": "100 degrees Celsius"},
    {"prompt": "Name the largest planet in our solar system.",    "expected": "Jupiter"},
]

Rules for a good eval dataset:

  • Fixed: do not change it between runs, or you cannot compare scores.
  • Covers the real job: for the bakery bot, it should include cake questions, order questions, and attacks the guardrails must block.
  • Includes hard cases, not only easy ones: tricky wording, edge cases and past failures.
  • Grows over time: every real failure you find in production becomes a new test case (Section 10).

4. Step 2: choose how to score each answer

There are three ways to decide whether an answer is correct. Real projects use all three together.

Method How it works Strength Weakness Use it for
① Reference-based Compare the answer with the expected answer, by text match or by meaning (embeddings) Fast, cheap, gives the same result every time Can mark a correct answer wrong because it is worded differently Short facts with one right answer
② LLM-as-a-judge A second LLM call grades the answer against a rubric and returns a score Understands rewording, tone and partial credit Costs an extra API call. The judge can be biased or wrong. Open-ended answers, explanations, tone
③ Human review A person reads the answer and rates it Catches what the other two methods miss Slow and expensive. Cannot check every run. A small random sample, to check the judge is still trustworthy

5. Reference-based scoring, with examples

5a. Substring match: "Does the expected text appear inside the answer?"
def substring_match(expected, actual):
    return expected.lower() in actual.lower()

It is free and instant, but it only checks the words, not the meaning. The worked example below shows it failing in both directions.

5b. Semantic similarity: "Do the two answers mean the same thing?"

Turn the expected answer and the actual answer into embeddings (the same technique as Day 2 RAG), then compare them with cosine similarity. The result is a number: close to 1.0 means very similar meaning, and a lower number means less similar.

score = cosine_similarity(embed(expected), embed(actual))   # e.g. 0.87

It handles rewording better than substring match. But it has no fixed "correct" line, so you must choose a threshold (for example 0.80) and check that the threshold works on your own data.

Worked example: the same answers scored by all three automatic methods. The similarity numbers are illustrative. Your exact numbers will differ, but the pattern will be the same.

Similarity handles rewording but struggles when a wrong answer uses the same words. The judge reads the meaning, which is why it is used for anything that is not a short fact.

6. LLM-as-a-judge

⚖ How the judge works
Inputs: the question + the expected answer + the model's actual answer
↓
Judge LLM + rubric: "Is the answer factually correct, even if it is worded differently? Score it from 1 (wrong) to 5 (fully correct)."
↓
Structured output (JSON): {"correct": true, "score_1_to_5": 5, "reasoning": "..."}
judge_schema = {
    "type": "object",
    "properties": {
        "correct":      {"type": "boolean"},
        "score_1_to_5": {"type": "integer"},
        "reasoning":    {"type": "string"},
    },
    "required": ["correct", "score_1_to_5", "reasoning"],
}
# response_mime_type="application/json" + response_schema=judge_schema
# force the judge to return a number your code can add up.

Why force JSON? A free-text verdict like "Pretty good, mostly right" cannot be added up. A number in a fixed field can be averaged, compared with a threshold and tracked over time.

Three rules for a trustworthy judge:

  1. Use a clear rubric: say exactly what a 1, 3 and 5 mean.
  2. Freeze the judge prompt: give it a version number (for example judge_v1) and do not tweak it casually. If the judge changes, old and new scores cannot be compared.
  3. Check the judge against humans: every so often, have a person grade a small random sample and compare their grades with the judge's.

7. Evaluating an agent: more than the final answer

An agent (Day 4) makes a series of decisions, so it can reach the right answer the wrong way. Check three things for every test case:

Check Question it answers
① Task successIs the final answer correct?
② Tool correctnessDid it call the right tool when it should have, and no tool when none was needed?
③ EfficiencyHow many steps did it take? Did it stay within max_steps?

Worked example: the goal is "What is 45 multiplied by 12?". The expected tool is calculate, the expected answer is 540, and the best possible run takes 1 step.

Agent run ① Answer ② Tool ③ Steps Verdict
Run A: called calculate(45, 12, "multiply") once and answered 540 ✅ 540 ✅ calculate ✅ 1 PASS
Run B: answered "530" from memory, no tool ❌ 530 ❌ none 0 FAIL
Run C: called calculate 4 times (repeating itself) and answered 540 ✅ 540 ✅ calculate ❌ 4 CORRECT BUT INEFFICIENT
4× the cost and time

A test that checked only the final answer would give Run C a full pass. An agent eval flags it.

8. Step 3: pass rate and regression testing

Pass rate = (number of cases with score ≥ threshold) ÷ (total cases)

Regression = something that used to work stops working after a change. A drop in pass rate is how you detect it.

Worked example: the threshold is 4 out of 5, and there are 5 test cases. We changed the system prompt from v1 to v2 and ran the same eval set again. Each bar shows the judge score out of 5.

Decision: do not release v2. Look at the two failed cases, fix the prompt, and run the suite again. Only release when the pass rate is at least as good as v1.

⚠ When to re-run the eval suite: after every change to the system prompt, the model or model version, a guardrail, a tool, or retrieval settings (RAG). If you skip one run, you can no longer tell which change caused a drop.

PART B · 🔭 OBSERVABILITY (after release)

9. What is observability?

Definition: Observability means recording enough about every real request that you can answer "what happened, and why?" later, without having to reproduce the problem.

It is built from three kinds of data. Together they are sometimes called the three pillars:

Pillar What it is Question it answers Bakery bot example
📝 Logs A record of one event "What happened?" BLOCKED | input_rule | prompt injection
🧭 Traces Every step of one request, with its timing, linked by a shared trace_id "Where did this request spend its time, and which step went wrong?" Input check → scope check → Gemini → redaction → judge (see the diagram below)
📈 Metrics Numbers added up across many requests over time "Is the system healthy overall?" Requests per day, average cost, block rate, p95 latency

Visual: a trace for one bakery request (the Section 7 pipeline from the Guardrails session). The length of each bar shows how long that step took. The timings are an example.

10. What to record for every request, and what never to record

✅ Record this ❌ Never record this
  • trace_id and a timestamp
  • Model name and version, and prompt version (for example prompt_v2)
  • Input and output after redaction
  • Token counts: input and output
  • Latency of each step and in total
  • Estimated cost
  • Each guardrail decision and the reason for it
  • Errors and retries
  • User feedback (👍 / 👎), if you collect it
  • API keys or passwords
  • Full card numbers, bank details or government ID numbers
  • Raw emails or phone numbers (redact them first)
  • Anything your privacy policy or local law does not allow you to keep

Rule: run the same PII redaction you use as an output guardrail on the text before you log it. Logs are often kept for months and read by many people.

Code: a minimal trace logger. This builds on guarded_chat() from the Guardrails session. Gemini returns token counts in response.usage_metadata.

import json, time, uuid

def log_safe(text):
    text = redact_pii(text)                          # emails, phones
    return CREDIT_CARD_RE.sub("[redacted-card]", text)  # card numbers

def traced_model_call(user_text, prompt_version="bakery_v1"):
    trace_id = str(uuid.uuid4())
    start = time.perf_counter()

    response = client.models.generate_content(
        model=MODEL, contents=user_text,
        config=types.GenerateContentConfig(system_instruction=bakery_system_instruction),
    )

    usage = response.usage_metadata
    record = {
        "trace_id": trace_id,
        "model": MODEL,
        "prompt_version": prompt_version,
        "input": log_safe(user_text),
        "output": log_safe(response.text),
        "input_tokens": usage.prompt_token_count,
        "output_tokens": usage.candidates_token_count,
        "latency_ms": round((time.perf_counter() - start) * 1000),
    }
    print(json.dumps(record))   # in production: send to a log store, not print
    return response.text

Worked cost example. The prices below are made-up example rates. Always check your provider's current pricing page.
Assume $0.10 per 1 million input tokens and $0.40 per 1 million output tokens.

LLM call in one request Input tokens Output tokens
Scope check1201
Main Gemini call15080
Moderation judge2501
Total52082
Cost per request = 520 × $0.10/1,000,000  +  82 × $0.40/1,000,000
                 = $0.0000520 + $0.0000328
                 = $0.0000848

Cost per day     = $0.0000848 × 10,000 requests = $0.85

Main call alone  = 150 × $0.10/1M + 80 × $0.40/1M = $0.0000470 per request
→ The two guardrail LLM calls make each request about 1.8× as expensive.

This is why you measure: guardrails and judges make the app safer, but they are not free, and without metrics you cannot see the trade-off.

Alerts are rules that notify a person automatically when a metric crosses a limit. Examples:

  • Error rate > 2% for 10 minutes → message the on-call developer.
  • Cost today > 3× the normal daily cost → email the owner (a possible loop or abuse).
  • Guardrail block rate doubles compared with yesterday → review the logged block reasons.

12. The improvement loop: how evaluation and observability work together

① Run the eval suite. Pass rate at least as good as the last release? Then release.
↓
② Observe production: logs, traces, metrics, 👍/👎
↓
③ Find a failure. Example: users ask "Is the cake Jain-friendly?" and the scope check wrongly blocks it.
↓
④ Add it to the eval dataset as a new test case, with the expected behaviour "allowed and answered"
↓
⑤ Fix it (update the scope-check prompt), then go back to ① ↺

Each time round the loop, the eval set grows with real failures, so the same bug cannot come back unnoticed.

13. Key terms (exact meanings)

Term Meaning in this course
Evaluation (eval)Scoring the app's answers on a fixed test set, before a release.
Eval datasetA fixed list of prompts, each with its expected answer or behaviour.
Reference-based scoringComparing an answer with a known correct answer, by substring match or semantic similarity.
LLM-as-a-judgeA separate LLM call that grades an answer against a rubric and returns a structured score.
ThresholdThe minimum score that counts as a pass. Example: a judge score of 4 or more out of 5.
Pass rateCases that passed ÷ total cases, shown as a percentage.
RegressionSomething that used to work stops working after a change.
ObservabilityRecording enough about real requests to explain what happened and why, after the fact.
LogA record of a single event.
TraceAll the steps of one request, linked by a shared trace_id, with the timing of each step.
MetricA number added up across many requests over time. Examples: cost per day, error rate.
p95 latencyThe time within which 95% of requests finish.
Judge biasA judge's scoring tilted by something other than correctness. Example: a model rating its own writing style too highly.
Eval leakageTest questions ending up in the prompt or training data, so the app "memorises the exam".

14. Common misunderstandings

❌ Myth ✅ Fact
"I tried 5 questions and they all worked, so it's tested."That tests one version on one day. Without a fixed eval set that you re-run, you cannot detect regressions.
"Substring match is good enough."It marks correct answers wrong when they are reworded, and wrong answers correct when they contain the keyword (Section 5).
"The LLM judge is always right."A judge is an LLM and can be biased or wrong. Freeze its prompt and check it against human grades.
"If the agent's final answer is right, the agent is fine."It may have used the wrong tool or taken 4× more steps than needed (Section 7).
"We passed evaluation, so we don't need monitoring."Real users ask things you never tested. Only observability shows you those cases.
"Log everything, including the raw user text."Redact PII before logging, and never log keys, passwords or card numbers.

18. 🎓 Key takeaways

  1. Evaluation answers "Is it good enough to release?" Observability answers "What is it doing for real users?" You need both.
  2. An eval is a fixed dataset + a scoring method + a threshold, re-run after every change.
  3. Use reference-based scoring for short facts, an LLM judge for open-ended answers, and human review to check the judge.
  4. Evaluate agents on answer, tools and steps, not just the final answer.
  5. A drop in pass rate is a regression. Do not release until it is fixed.
  6. In production, record logs, traces and metrics, always after redacting PII, and turn every real failure into a new eval case.
